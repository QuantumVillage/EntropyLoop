# Health tests (NIST SP 800-90B, sections 4.3 and 4.4)

The firmware hashes raw ADC samples with SHA-512. Hashed output passes `ent` and NIST STS whether or not the physical source is working, so those suites cannot tell you if the laser, fibre, detector or ADC has failed. Health tests run on the **raw samples before hashing** and stop output when the source misbehaves.

## What runs

| Test | Catches | Rule |
|---|---|---|
| Start-up test (4.3) | A source that is broken at power-on | Each channel's first 1,024 samples must pass both tests below. They are discarded. That channel's output starts only after a pass. |
| Repetition Count Test (4.4.1) | Stuck ADC, a dead input, saturation | Fail if one value repeats `C_RCT` times in a row |
| Adaptive Proportion Test (4.4.2) | Loss of entropy where values are not stuck but too predictable | In each 512-sample window, fail if the window's first value appears `C_APT` times |

The tests run separately on each ADC channel, with their own state, because the two channels are independent sources. Any batch (1,024 samples) with a failure is **discarded**: it is not hashed or sent. The device prints instead:

```
HEALTH: FAIL APT | R:   41 | CH0 | RCT fails: 0 | APT fails: 3
```

The line starts with `HEALTH:`, so the `H_min:` parsers in `python-scripts/` ignore it. Normal `H_min: ... | R: ... | CHn | Data:` output is unchanged. The existing range squelch and `MIN_ENTROPY_FLOOR` are kept; the checks catch different faults (see below).

The MCP server's `SAMPLE_RE` is updated in two ways:
- it accepts the optional `CHn |` field (without it, the dual-channel output did not match at all);
- it stops at a `HEALTH:` line, so a failure line does not swallow the good sample before it.

## Cutoffs

Cutoffs depend on the claimed min-entropy per sample, `H`, and the false-alarm rate `alpha` (90B recommends 2^-20 to 2^-40). The firmware uses **alpha = 2^-40**, because at roughly 500,000 samples per second, 2^-20 would allow a false alarm about every two seconds in the worst case.

| Claimed H (bits per 12-bit sample) | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| RCT cutoff | 41 | 21 | 15 | 11 | 9 | 8 | 7 | 6 |
| APT cutoff (W = 512) | 336 | 201 | 123 | 78 | 51 | 35 | 26 | 19 |

Generated by `tools/ht_cutoffs.py` with exact arithmetic and checked against `scipy.stats.binom`. At alpha = 2^-20 the tool reproduces the 90B values (for example H = 4: RCT 6, APT 62). Regenerate the header with:

```
python3 tools/ht_cutoffs.py --table --c-header > src/health_cutoffs.h
```

**Default: `HT_CLAIMED_H 4`** in `src/main.c`. An independent 800-90B assessment of one public EntropyLoop capture ([EntropyLoop issue #3](https://github.com/QuantumVillage/EntropyLoop/issues/3), [results](https://github.com/kalash33/entropyloop-assessment)) estimated about 6 bits of min-entropy for the low 8 bits of each sample. 4 is set below that so that builds with a weaker signal do not raise false alarms. Assess your own device before raising it. A higher `H` catches subtler faults but raises false alarms if the source is weaker than claimed.

## Simulated faults

`make -C tests demo` feeds synthetic sources through the tests, 10,240,000 samples each. These are models, not measurements of an EntropyLoop.

| Source (synthetic) | H | First failure at sample | Batches blocked by health tests | Batches squelched (range < 200) |
|---|---|---|---|---|
| healthy, sd 78 (like issue #3 data) | 4 | none | 0.00% | 0.00% |
| healthy, sd 78 (like issue #3 data) | 6 | none | 0.00% | 0.00% |
| healthy, sd 300 (wider signal) | 4 | none | 0.00% | 0.00% |
| healthy, sd 300 (wider signal) | 6 | none | 0.00% | 0.00% |
| stuck ADC (constant 2048) | 4 | 11 (RCT) | 100.00% | 100.00% |
| stuck ADC (constant 2048) | 6 | 8 (RCT) | 100.00% | 100.00% |
| low noise, sd 2 | 4 | 344 (APT) | 78.32% | 100.00% |
| low noise, sd 2 | 6 | 159 (APT) | 98.03% | 100.00% |
| low noise, sd 10 | 4 | none | 0.00% | 100.00% |
| low noise, sd 10 | 6 | 539133 (APT) | 0.10% | 100.00% |
| alternating 0 and 4095 | 4 | 155 (APT) | 100.00% | 0.00% |
| alternating 0 and 4095 | 6 | 69 (APT) | 100.00% | 0.00% |
| 30% clipped at rail, sd 78 | 4 | 5380 (APT) | 52.15% | 0.00% |
| 30% clipped at rail, sd 78 | 6 | 5235 (APT) | 54.43% | 0.00% |
| 5% clipped at rail, sd 78 | 4 | none | 0.00% | 0.00% |
| 5% clipped at rail, sd 78 | 6 | 150493 (APT) | 0.48% | 0.00% |

What this shows:
- No false alarms on the healthy models.
- The health tests catch faults the range squelch misses: a signal that swings across the full range but carries little entropy (alternating values, heavy clipping).
- The squelch catches a low-amplitude signal that the health tests at H = 4 allow. **Keep both.**
- Neither check proves the entropy is quantum. They detect a broken or degraded source.

## Real data: no false alarms

The tests were replayed on the five 1,000,000-sample windows of the public issue #3 capture used for the 800-90B assessment ([results](https://github.com/kalash33/entropyloop-assessment/blob/main/results/health_replay.txt), run in GitHub Actions).

| Claimed H | RCT cutoff | APT cutoff | Failures (5M samples) | Longest repeat | Highest APT count |
|---|---|---|---|---|---|
| 4 | 11 | 78 | 0 | 3 | 9 to 12 |
| 6 | 8 | 35 | 0 | 3 | 9 to 12 |

The real data stays well inside even the stricter H = 6 cutoffs. This shows the tests do not misfire on this healthy capture. It does not show what they catch on real faults; that needs fault data from a device.

## Replay a real capture

```
make -C tests replay
tests/replay capture.bin 4            # little-endian uint16, 12-bit values
```

## Host tests

```
make -C tests test        # 37 checks: cutoff table, RCT/APT boundaries, start-up, masking, no false alarms over 40M healthy samples
```

Also checked: clean under `-Wall -Wextra -Werror -Wconversion` with `arm-none-eabi-gcc -mcpu=cortex-m0plus`, and under AddressSanitizer and UndefinedBehaviorSanitizer on the host. The firmware builds with Pico SDK 2.2.0. The library adds 486 bytes of code and no heap use.

## Not yet done

- Not yet run on hardware. Cycle cost per sample on the RP2040 has not been measured.
- Recovery policy is simple: bad batches are dropped and testing continues. A product might latch an error after repeated failures.
- The MicroPython script (`python-scripts/QRNG.py`) is handled in a separate change.
